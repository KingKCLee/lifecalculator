## 1. 입력 항목
- 입력 칸이 아니라 화면 동작이 사양이다: "달력 보기 / 날짜 전체 보기" 링크, "이전달 / 다음달" 링크, "윤달 전체 포함" 체크(leapAll). 이전·다음달은 서버의 현재 월 기준 상대 이동이다. [측정: 표본 s01~s09 screen.values, notes/손없는날.md]
- 우리 쪽: 연도 select(올해 -1 ~ +3), 월 select, 강조 기준 토글(손없는 날 전체 / 이사 최적 = 손없는 날+금·토·일). [측정: CalcLuckyDay.jsx, ours 표본 화면]

## 2. 계산식 정리
- 그쪽: 달력 칸마다 "음력 M월 D일"을 붙이고, 음력 일이 9·10·19·20·29·30 인 날에 강조 표시한다. 한 달 안에서 양력 일자 기준으로 표시된 칸을 읽었다 [측정: s01 mainText 의 .lunar 목록].
- 우리: 브라우저 Intl 의 'chinese' 달력으로 양력->음력 일(日)을 구해 9·19·29 일만 손없는 날로 표시한다 [측정: CalcLuckyDay.jsx:9~19 LUCKY_DAYS=[9,19,29], lunarFmt]. 시간대를 지정하지 않으며 중국 기준시 규칙의 달력이다 [측정: 코드 읽기와 CalcLunar.jsx:5 주석].
- 음력 변환 자체는 별도 문서(음력_달력.md)의 판정과 같은 원인으로 어긋난다.

## 3. 상수·구간표

## 6. 판정과 불일치 예시
- 판정: 불일치 (비교 7건 중 4건 일치, 3건 불일치). 일치 기준은 공통 음력일(9·19·29)의 양력 일자 집합이다. 그쪽 6일 전체와 우리 3일 전체를 그대로 대조하면 비교한 7개월 모두 집합이 달라 0건 일치다(10·20·30일 차이).
- 불일치 예시: 2026년 10월 -> 그쪽 음력 9일·19일이 양력 19일·29일 vs 우리 18일·28일 (하루 차이). 같은 달 안에서 음력 8월 30일을 그쪽은 10월 10일에 두고 우리는 10월 10일을 9월 1일로 센다. 원인 추정: 우리 코드가 쓰는 Intl 'chinese' 달력은 중국 기준시(UTC+8)로 월 경계를 정하는데, 2026-10-10 신월 시각이 한국시간으로는 11일 00시 50분 무렵이라 하루가 갈린다 [추측: 원인; 측정: 한국천문연구원 달력자료 9월 1일=2026-10-11, law/음력.json].
- 기준 차이: 손없는 날 정의(6일 vs 3일), 윤달 처리(그쪽 윤달 칸에 음력 표기, 우리 윤달 옵션 없음) [측정: s08].
